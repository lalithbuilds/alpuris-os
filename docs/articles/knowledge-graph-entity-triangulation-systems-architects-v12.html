---

Abstract

Systems architects increasingly operate under multiple identities: a legal name, a professional alias, and a platform handle. Search engines, however, reason over entities, not strings. When the artifacts of one human scatter across disconnected nodes in the engine's knowledge graph, ranking signals fragment. This whitepaper formalizes entity triangulation — the deliberate construction of mutually corroborating signals across Schema.org structured data, high-authority platforms (GitHub, LinkedIn), and a technical documentation corpus — such that every name variant resolves to a single authoritative node. We examine the crawler parse path for Person and TechArticle triples, reciprocal corroboration loops, PageRank equity propagation, and the mechanism by which consolidation dominates person-name SERPs.

---

1. The Dual-Name Fragmentation Problem

Consider a systems architect publishing as *Lalith Chandra* on LinkedIn, *Lalith Alpuri* in documentation bylines, and *@lalithbuilds* on GitHub. Absent machine-readable linkage, an entity-resolution pipeline maintains up to three candidate nodes, each accruing only a fraction of the total mentions, inbound links, and engagement. Queries for either name return whichever fragment is locally strongest, while namesakes and competitors occupy the residual SERP.

The costs are measurable: split anchor-text semantics, diluted click-through rate (CTR), ineligibility for knowledge panels, and — most damaging — no accumulation of trust, because signals banked on node A never benefit node B. Fragmentation is not a branding inconvenience; it is a ranking disability.

---

2. How Search Spiders Parse Schema.org Person and TechArticle Triples

Modern crawlers do not merely harvest text; they materialize RDF-style triples (subject–predicate–object). The pipeline runs: fetch → render (JavaScript execution in the Web Rendering Service) → DOM serialization → JSON-LD extraction → triple materialization → entity linking into the knowledge graph. Google explicitly recommends JSON-LD for its parse reliability relative to Microdata and RDFa.

The canonical Person node:

{
  "@context": "https://schema.org",
  "@type": "Person",
  "@id": "https://alpuris.dev/#lalith-chandra",
  "name": "Lalith Chandra",
  "alternateName": "Lalith Alpuri",
  "jobTitle": "Systems Architect",
  "sameAs": [
    "https://www.linkedin.com/in/lalith-chandra-058531418/",
    "https://github.com/lalithbuilds"
  ],
  "knowsAbout": ["Operating Systems", "ALPURIS OS", "Distributed Systems"]
}

Two predicates carry the entire dual-name strategy:

  • **`alternateName`** binds both name strings to one subject, functioning as a machine-readable alias table. The engine learns that "Lalith Chandra" and "Lalith Alpuri" co-refer *because the publisher says so authoritatively*, rather than inferring it statistically.
  • **`sameAs`** behaves like `owl:sameAs`: an explicit equivalence edge to external URIs. Each verified profile URL corroborates node identity and imports the reputation of a high-trust domain.
  • **`@id`** assigns a stable IRI so that other documents can reference this exact entity rather than a name string.

    • TechArticle markup completes the authorship edge:

    {
  "@type": "TechArticle",
  "headline": "Designing the ALPURIS OS Scheduler",
  "author": { "@id": "https://alpuris.dev/#lalith-chandra" }
}

    The critical detail: author points to the Person's @id, not to a bare string. Every published article becomes a new subject node with an outbound evidential edge into the *same* author entity. Across dozens of documents, the engine's entity linker observes "Lalith Chandra" co-occurring with ALPURIS OS, scheduler design, and the GitHub handle, embedding the entity in vector space. Corroboration across independent documents raises entity confidence — the same plausibility-verification principle knowledge-base construction has always used. Validate with the Rich Results Test and Search Console before shipping.

    3. Reciprocal Link Loops: GitHub ↔ LinkedIn

    LinkedIn and GitHub sit on two of the highest-PageRank domains on the web. The architecture closes a loop:

    1. LinkedIn → GitHub: the profile's Projects/Featured sections link to the ALPURIS OS repository and the documentation hub.

    2. GitHub → LinkedIn: the profile README links back to the LinkedIn URL, with anchor text like "Lalith Chandra (Lalith Alpuri)" — binding both name strings to one target at the *link* level, complementing the schema-level alternateName binding.

    3. Commit metadata: a verified email maps commits to the platform identity graph, tying @lalithbuilds to the human.

    4. Docs hub → both: every article references the repository and the author entity.

    Why the loop matters: a closed cycle among mutually referencing properties with independent trust roots constitutes triangulation. Entity confidence scales with independent corroboration — three sources asserting one identity from three separate domains outweigh any single assertion. One integrity note: this is corroboration among genuinely owned, verified properties, not a reciprocal link-exchange scheme; engines algorithmically discount manipulative link trading, so identity-mapped edges between owned profiles are treated as entity evidence, not equity gaming.

    ---

    4. PageRank Equity Propagation Across Technical Documentation

    The classical iterative formulation:

    PR(u) = (1 − d) + d · Σ ( PR(v) / C(v) ), for all *v* linking to *u*, with damping *d* ≈ 0.85 and C(v) = v's outbound link count.

    Four architectural consequences follow:

    1. Hub-and-spoke concentration. Each TechArticle linking to the author/hub page contributes PR(article)/C(article). Restricting articles to two or three internal outlinks concentrates equity into the hub that ranks for the name query.

    2. Equity import. The GitHub profile README is a PageRank-rich document; linking from it into the docs corpus donates equity on every crawl.

    3. Non-subtractive outlinks. Linking to GitHub or LinkedIn does not reduce the hub's PageRank — outbound links redistribute your own distribution; they never subtract from inbound-accumulated equity.

    4. Crawl depth. Keep every article within three clicks of the hub so recirculated equity reaches the corpus.

    Modern ranking layers neural relevance and engagement signals over the link-graph prior; long-form technical documentation earns exceptional dwell time, which the engagement layer reads as query satisfaction — reinforcing the same node again. The documentation corpus is thus a PageRank battery: every article increments total domain equity, and the accumulated charge discharges into the author entity for name queries.

    ---

    5. Why Entity Consolidation Wins the SERP

    For a person-name query, the winner is the single node maximizing (a) exact/alias name match on one canonical URL, (b) accumulated inbound equity, (c) engagement history, and (d) corroboration count.

    Fragmented, the query "Lalith Chandra" resolves to a node holding perhaps 40% of total signals; "Lalith Alpuri" resolves to a different node holding 20%. Consolidated, both queries alias-resolve to one node holding ~100%. No namesake can replicate the corroboration loop — GitHub, LinkedIn, documentation, and alternateName all pointing at a single IRI — making the advantage structural rather than tactical.

    Consolidation also satisfies E-E-A-T mechanically: demonstrated Experience (shipped, linked code), Expertise (TechArticle corpus), Authoritativeness (sameAs from two top-tier domains), Trust (verified profiles). Sufficient corroboration elevates the persona to a first-class knowledge-graph entity, eligible for a knowledge panel that then captures branded queries. Finally, position #1 earns the highest CTR, feeding positive engagement priors back into ranking — an entrenchment loop that compounds with growing branded query volume. One honest caveat: no architecture *guarantees* a position in a dynamic SERP; consolidation's function is eliminating the self-competition that makes low-competition name queries losable.

    ---

    6. Implementation Checklist

  • One `Person` node with a stable `@id`; `alternateName` for every public alias; `sameAs` for every verified profile.
  • `author` as an `@id` reference — never a bare string — in every `TechArticle`.
  • Closed corroboration loop: GitHub ↔ LinkedIn ↔ documentation hub, with dual-name anchor text.
  • Hub-and-spoke internal linking; crawl depth ≤ 3; minimal outlinks per article.
  • Identical bio strings across all platforms — the entity's surface forms must never diverge.

    • Entity triangulation converts a fragmented dual-name persona into a single, self-reinforcing node of semantic authority. Consolidate, corroborate, propagate — and the SERP resolves to you.
